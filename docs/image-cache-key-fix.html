● MOMOGO iOS · Issue #80 · fix/080-image-caching

이미지 캐시 키를 presigned URL 대신 photoId로 고정했다

서버가 매 요청마다 서명을 새로 굽는 presigned URL 때문에, Kingfisher가 캐싱을 하고도 매번 재다운로드하던 문제. 캐시 키를 URL에서 photoId로 옮겨 고쳤다.

커밋 완료 PR 대기 Kingfisher 7.12.0

증상

오늘 화면을 나갔다 돌아오면, 사진이 처음부터 다시 로딩된다

그룹상세에서 어제 날짜를 봤다가 오늘로 돌아오면 이미 봤던 사진인데도 매번 다시 받아온다. Kingfisher가 캐싱 라이브러리인데 왜 캐싱이 안 되는지가 출발점이었다.

원인 — 실측

서버는 같은 사진에 매번 다른 서명을 붙여 내려준다

그룹상세를 오늘 → 어제 → 오늘로 왕복하며 서버 응답을 그대로 찍어봤다. 같은 photoId=4인데, 6초 차이의 두 응답이 내려준 downloadUrl은 오브젝트 경로만 같고 쿼리스트링(서명)이 다르다.

photoId=4, 1차 (02:19:49)
  .../users/7/2026-08-17/64b5ce52-…-70307353d654.jpg
  ?X-Amz-Date=20260816T161949Z
  &X-Amz-Signature=fb9b8a4a944903c4a619c9759d5bd1c27aaf093…

photoId=4, 2차 (02:19:55, 6초 뒤)
  .../users/7/2026-08-17/64b5ce52-…-70307353d654.jpg
  ?X-Amz-Date=20260816T161955Z
  &X-Amz-Signature=403c348be7d16d4d756fb735779b699270b669e…

Cloudflare R2 presigned URL이라 X-Amz-Expires=900(15분)짜리 서명을 호출할 때마다 새로 굽는다. 오브젝트 경로(=photoId)는 고정, 서명만 매번 다르다.

그런데 Kingfisher(7.12.0)는 기본적으로 URL 문자열 전체를 캐시 키로 쓴다. 서명이 바뀌면 문자열이 달라지니, 같은 사진이어도 매번 "처음 보는 키"로 취급돼 무조건 미스가 난다.

해결

캐시 키를 URL에서 photoId로 옮긴다

새 헬퍼 하나로 캐시 키 포맷을 한 곳에서 강제한다. 이미지를 그리는 3곳(그룹상세 그리드, 신고 화면, 홈 최근사진) 전부 이걸 거치게 했다.

enum RemotePhotoSource {
    static func make(photoId: Int, downloadURL: URL) -> Source {
        downloadURL.convertToSource(overrideCacheKey: "photo-\(photoId)")
    }
}

캐시 키 — 수정 전

1차 = …fb9b8a4a…
2차 = …403c348b…

1차 ≠ 2차 → 미스, 재다운로드

캐시 키 — 수정 후

1차 = photo-4
2차 = photo-4

1차 = 2차 → 히트, 즉시 표시

동작 원리

조회·저장은 항상 cacheKey, 네트워크만 downloadURL

Kingfisher 소스(KingfisherManager.swift, ImageCache.swift)를 직접 따라가 보면, 캐시 조회와 저장 양쪽 다 source.cacheKey만 쓴다. downloadURL은 캐시가 완전히 비어있을 때 실제로 파일을 받아오는 주소로만 쓰인다 — 그래서 서명이 매번 달라도 무관하다.

저장 위치까지 보면 더 명확하다 — 메모리는 NSCache<NSString, …>에 "photo-4" 문자열을 그대로 키로 쓰고, 디스크는 그 문자열을 MD5 해시한 값을 파일명으로 쓴다. 둘 다 downloadURL은 계산에 아예 관여하지 않는다.

왜 안전한가

photoId는 삭제 전까지 내용이 안 바뀌는 값이다

키를 photoId로 영구 고정해도 되는 이유는 만료 정책이 아니라 photoId가 가리키는 이미지가 절대 제자리에서 바뀌지 않기 때문이다. 두 가지 근거를 코드에서 확인했다.

  • 삭제는 실제로 "지우기"가 아니라 연결 해제다. DELETE /groups/{groupId}/photos/{photoId} — 그룹에서만 떼어낼 뿐, photo 레코드 자체는 서버에 남는다.
  • 재업로드는 항상 새 photoId를 받는다. photoId는 업로드 3단계 중 마지막 confirm 응답에서만 발급된다 — 앞 두 단계엔 아예 존재하지 않는 값이다.
POST /photos/upload-urlspresigned PUT URL 발급
→
PUT (R2)바이너리 업로드
→
POST /photosphotoId 발급 (여기서만)

objectKey에도 랜덤 해시가 들어가 같은 경로가 재사용될 수 없다. 재업로드=새 photoId라는 전제가 코드로 보장된다.

실측 검증

같은 화면을 두 번 왕복해도 네트워크는 한 번만 탔다

수정한 빌드를 실기기에 올려 그룹상세를 오늘 → 어제 → 오늘로 왕복시키고, KFImage의 onSuccess 콜백이 주는 실제 cacheType을 찍었다(검증 뒤 제거).

02:09:45  GET /groups/141?date=2026-08-16   200   어제로 이동
02:09:48  GET /groups/141                    200   오늘로 복귀
          [ImageCacheProbe] photoId=38 cacheType=memory

같은 왕복을 6초 뒤 한 번 더 반복해도 결과는 동일하게 cacheType=memory였다 — 서버가 그사이 새로 서명한 downloadUrl을 내려줬는데도, 이미지 다운로드는 한 번도 다시 일어나지 않았다.
